# ENGINEERING ROADMAP

这份文档用于把当前项目的工程治理建议收敛成一份可执行路线图。

目标：

- 把“知道哪里有问题”变成分阶段推进计划
- 给技术负责人、前后端负责人、CI/测试负责人一个统一执行口径
- 避免治理工作在新需求压力下反复中断

## 1. 当前判断

项目当前状态不是“缺少架构”，而是“已有架构方向，但工程纪律尚未完全收口”。

已经具备的基础：

- 前后端边界意识已经建立
- 文档和代码组织基本对齐
- CI 已覆盖 lint、构建、前端测试、后端单测、HTTP 测试、MySQL 集成测试
- 核心业务链路不是 demo 级实现，而是持续演进中的业务系统

当前最突出的问题：

- 主干虽然已经恢复绿色，但剩余复杂度热点集中在少数后端中枢
- 部分中枢文件复杂度过高，已经开始影响可维护性
- 核心路径已有测试，但还没有形成足够厚的回归保护网
- 当前已经进入“防反弹门禁”阶段，需要把 warning 基线和热点文件保护固化到 CI

因此当前三阶段目标是：

1. `1周`：止血，恢复质量基线
2. `1个月`：收口，让核心路径进入可维护状态
3. `3个月`：规模化，把治理要求固化为团队协作机制

## 2. 阶段一：1周

阶段目标：

- 恢复主干可交付状态
- 停止高风险文件继续变胖
- 把“口头要求”变成最小可执行规则

### 2.1 本阶段任务表

| 事项 | 建议负责人 | 输出物 | 验收标准 | 主要风险 |
|---|---|---|---|---|
| 修复 `lint` 阻塞错误 | 前端负责人 | 修复 PR | `npm run lint` 不再因 error 失败 | 历史 warning 多，容易扩大改动范围 |
| 冻结高风险中枢继续膨胀 | Tech Lead | 评审约束说明 | 指定中枢文件只允许拆分，不允许继续堆业务逻辑 | 新需求插队导致治理中断 |
| 建立“新增代码不得变差”规则 | Tech Lead + CI 负责人 | CI 规则更新 | 新 PR 不新增 lint error；复杂度超阈值的新增函数不允许合并 | 老代码基线脏，执行上容易妥协 |
| 修首页按需加载缺口 | 前端负责人 | 首页优化 PR | 示例数据改为展开时加载，首屏不再同步带入完整样例数据 | 动态加载后需关注交互体验 |
| 建质量看板 | 技术经理 | `docs/quality-baseline.md` | 至少记录 lint error/warning、复杂度热点、体积热点、目标日期 | 只记录不跟进，文档会失效 |

### 2.4 当前阶段补充动作

在当前基线已收敛到 `0 warnings, 0 errors` 的情况下，阶段一还应追加两条最小门禁：

- 新 PR 不允许新增 warning
- touched files warning 数不得增加

这两条规则的目标不是“立刻把 warning 清零”，而是先阻止基线反弹。

### 2.2 建议重点盯防文件

这些文件一周内不应该再继续变胖：

- [client/src/components/BatchGradingPage.jsx](client/src/components/BatchGradingPage.jsx)
- [client/src/api/client.js](client/src/api/client.js)
- [client/src/components/FeedbackView/AnalysisTab.jsx](client/src/components/FeedbackView/AnalysisTab.jsx)
- [server/services/writingSubmissionService.js](server/services/writingSubmissionService.js)

### 2.3 本阶段验收口径

只看 4 个硬结果：

- `lint error = 0`
- 主干 CI 恢复绿色
- 首页首屏无效负载下降
- 高风险中枢文件停止继续堆逻辑

## 3. 阶段二：1个月

阶段目标：

- 把局部优秀结构变成整体可维护结构
- 把关键路径从“能改”推进到“可稳定改”
- 给未来功能迭代留出明确挂载点

### 3.1 本阶段任务表

| 事项 | 建议负责人 | 输出物 | 验收标准 | 主要风险 |
|---|---|---|---|---|
| 拆 `BatchGradingPage` | 前端负责人 | 页面分层 PR | 页面拆成 `page / model / result panels / export actions`，主文件明显瘦身 | 状态与导出行为易回归 |
| 拆 `client/src/api/client.js` | 前端基础设施负责人 | API 层拆分 PR | `request / download / stream / error normalization` 分离，公共 API 层复杂度下降 | SSE 兼容性与错误处理回归 |
| 拆 `AnalysisTab` | 前端模块负责人 | 分析渲染重构 PR | 类型判断、fallback、组件注册分离，新增类型不再依赖大分支 | 写作类型回退易被改坏 |
| 拆 `writingSubmissionService` | 后端负责人 | service 内部拆分 PR | 输入归一化、权限校验、作业关联、持久化、后续队列分离 | 跨表流程复杂，回归成本高 |
| 抽前端 UI primitive | 前端负责人 | 基础 UI 层 | 高频卡片、按钮、表单、badge 进入统一组件和 token 层 | 半新半旧过渡期会风格割裂 |
| 补关键链路测试 | QA + 前后端负责人 | 测试 PR | 覆盖批量批改、作文提交、FeedbackView 回退、SSE 异常 | 测试补齐速度可能跟不上需求 |
| 建性能基线 | 前端基础设施负责人 | 构建体积与首包报告 | 固定首页首包、关键 chunk、总构建体积指标 | 如果无阈值，报表价值有限 |

### 3.2 这个阶段不建议做的事

- 不做全仓库“一次性统一重构”
- 不做全量大规模样式迁移
- 不把所有 warning 作为同一批任务硬清空
- 不在没有测试护栏的情况下重写核心流程
- 不为了把 `20+` warning 压成 `0` 而做碎修

### 3.3 本阶段验收口径

只看 3 件事：

- 核心中枢复杂度是否实际下降
- 高风险链路测试是否补厚
- 新功能接入是否开始依赖清晰挂载点，而不是继续把逻辑塞回 page/service 中枢

## 4. 阶段三：3个月

阶段目标：

- 把工程治理从“专项任务”升级为“团队默认工作方式”
- 让系统具备更稳定的协作、发布和排障能力
- 降低未来继续扩人扩模块时的认知成本

### 4.1 本阶段任务表

| 事项 | 建议负责人 | 输出物 | 验收标准 | 主要风险 |
|---|---|---|---|---|
| 建模块 owner 制度 | Tech Lead | 模块责任表 | 关键目录和中枢模块都有 owner，变更路径清晰 | 责任不清会继续依赖熟悉项目的人硬撑 |
| 稳定 API contract | 前后端负责人 | DTO/错误码/状态枚举约定 | `auth / assignment / workbench / feedback / batch grading` 有清晰契约 | 旧接口兼容处理成本高 |
| 建可观测性闭环 | 后端负责人 | 指标与告警方案 | 能看到接口耗时、AI 成功率、队列积压、导出失败率、前端错误 | 只采集不消费，告警会失去意义 |
| 升级发布门禁 | CI 负责人 | 完整门禁链路 | lint、单测、HTTP、MySQL、build、体积检查不过不允许合并 | 初期会降低合并速度 |
| 做技术债清账 | Tech Lead | 债务关闭记录 | 巨型文件与模糊边界模块至少完成一轮收敛 | 新需求会持续挤压治理窗口 |

### 4.2 三个月后应达到的工程状态

- 关键模块都有明确 owner
- 中枢文件不再成为默认功能落点
- 契约边界更稳定，前后端不再频繁靠猜返回结构协作
- 线上问题可通过日志、指标、告警快速定位
- 合并主干依赖质量门禁，而不是依赖熟悉代码的人兜底

## 5. 推荐角色分工

### 5.1 Tech Lead

职责：

- 定阶段优先级
- 定中枢文件保护规则
- 卡评审标准
- 在需求压力和治理任务之间做取舍

不应该把时间主要花在：

- 零散修格式
- 替代所有模块负责人做具体拆分

### 5.2 前端负责人

职责：

- 推进高风险页面和公共 API 层拆分
- 推进 UI primitive 与 token 层建设
- 建前端性能基线
- 保证核心用户路径的交互不回退

### 5.3 后端负责人

职责：

- 推进高风险 service 拆分
- 稳定关键 API contract
- 建后端可观测性和错误定位能力
- 补足高风险业务链路测试

### 5.4 CI / 基础设施负责人

职责：

- 把 lint、测试、构建、体积检查变成门禁
- 维护质量趋势报表
- 让规则变成默认流程，而不是人工提醒

### 5.5 QA / 业务负责人

职责：

- 确认关键用户路径回归清单
- 参与定义阶段验收口径
- 避免治理任务只对代码结构负责、不对真实用户路径负责

## 6. 推荐执行节奏

### 6.1 每周质量例会

只看红黄绿，不做泛泛汇报。

建议固定查看：

- lint error / warning 变化
- 主干 CI 状态
- 最大复杂度热点变化
- 关键回归缺陷

### 6.2 每两周架构 review

只看边界是否被破坏。

重点问题：

- 新逻辑是否又塞回 page / coordinator / service 中枢
- 高风险文件是否继续变胖
- 新模块是否找到了正确挂载层

### 6.3 每月阶段复盘

只确认基线是否真的提升。

建议复盘问题：

- 哪些治理动作真正降低了维护成本
- 哪些规则执行不下去，原因是什么
- 哪些模块还在持续反复回归

---

## 7. 当前推荐跟踪指标

建议至少跟踪以下指标：

- `lint error` 数
- `lint warning` 数
- 复杂度超阈值函数数量
- 超大文件数量
- 首页首包体积
- 关键 chunk 体积
- 主干 CI 绿色率
- 批量批改链路回归缺陷数
- 作文提交链路回归缺陷数
- 导出失败率

建议同时固定跟踪：

- 当前 lint warning budget
- 超预算 PR 次数
- 热点文件是否继续增长

这些指标的目标不是“做报表”，而是帮助判断治理是否真正减少了项目维护成本。

---

## 8. 当前建议的执行原则

- 先修阻塞质量问题，再谈结构美化
- 优先治理高风险中枢，不做全仓库平均用力
- 没有测试护栏时，不大改关键业务路径
- 架构文档必须跟随阶段性治理结果更新
- 规则必须进入 CI 或 review 机制，否则很快失效

## 9. 下一步建议

如果要把这份路线图继续推进为执行面材料，建议补两份配套文档：

1. `docs/quality-baseline.md`
   记录当前 lint、复杂度、体积、CI 基线

2. 最新 handoff 文档
   记录当前高风险文件、已知问题、阶段性治理优先级

这样后续无论是人类程序员接手，还是 AI 连续修改，都能快速知道：

- 当前阶段目标是什么
- 哪些文件不能继续变胖
- 哪些治理动作是当前优先级最高的
